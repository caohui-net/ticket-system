## 1. 设计概述

### 1.1 设计原则

- **规范化设计**: 符合第三范式（3NF），避免数据冗余
- **可扩展性**: 支持未来功能扩展（如工单模板、SLA等）
- **性能优化**: 合理设计索引，优化查询性能
- **数据完整性**: 使用外键约束、唯一约束、非空约束保证数据一致性
- **审计追踪**: 所有表包含创建时间、更新时间字段
- **软删除**: 关键表支持软删除（deleted_at字段）

### 1.2 核心实体

本系统共设计 **9 张核心表**：

| 表名 | 中文名 | 用途 |
|------|--------|------|
| `users` | 用户表 | 存储系统用户信息 |
| `roles` | 角色表 | 定义系统角色 |
| `user_roles` | 用户角色关联表 | 多对多关系（用户-角色） |
| `tickets` | 工单表 | 工单核心数据 |
| `ticket_logs` | 工单操作日志表 | 记录所有工单操作 |
| `ticket_attachments` | 工单附件表 | 存储附件元数据 |
| `notifications` | 通知表 | 系统通知记录 |
| `ticket_assignments` | 工单分配记录表 | 记录分配历史 |
| `system_settings` | 系统配置表 | 存储系统参数 |

### 1.3 关系总览

```
users (1) ←→ (N) user_roles (N) ←→ (1) roles
users (1) ←→ (N) tickets (创建者)
users (1) ←→ (N) tickets (处理人)
users (1) ←→ (N) tickets (审核人)
tickets (1) ←→ (N) ticket_logs
tickets (1) ←→ (N) ticket_attachments
tickets (1) ←→ (N) ticket_assignments
tickets (1) ←→ (N) notifications
users (1) ←→ (N) notifications (接收者)
```

### 2.2 关系说明

#### 2.2.1 用户与角色（多对多）
- 一个用户可以拥有多个角色（如：某人既是处理人，又是审核人）
- 一个角色可以分配给多个用户
- 通过 `user_roles` 中间表实现多对多关系

#### 2.2.2 用户与工单（一对多）
- **创建者关系**: 一个用户可以创建多个工单
- **处理人关系**: 一个用户可以处理多个工单
- **审核人关系**: 一个用户可以审核多个工单
- 一个工单只有一个创建者、一个处理人、一个审核人（当前状态）

#### 2.2.3 工单与子表（一对多）
- 一个工单可以有多条操作日志
- 一个工单可以有多个附件
- 一个工单可以有多次分配记录（重新分配）
- 一个工单可以触发多条通知

## 3. 表结构详细设计

### 3.1 用户表（users）

**用途**: 存储系统所有用户信息

**表名**: `users`

| 字段名 | 数据类型 | 长度 | 允许NULL | 默认值 | 说明 |
|--------|----------|------|----------|--------|------|
| `user_id` | BIGINT | - | NO | AUTO_INCREMENT | 用户ID（主键） |
| `username` | VARCHAR | 50 | NO | - | 用户名（唯一，登录用） |
| `password` | VARCHAR | 255 | NO | - | 密码（BCrypt加密） |
| `real_name` | VARCHAR | 50 | NO | - | 真实姓名 |
| `email` | VARCHAR | 100 | NO | - | 邮箱（唯一） |
| `phone` | VARCHAR | 20 | YES | NULL | 手机号 |
| `department` | VARCHAR | 50 | YES | NULL | 部门 |
| `avatar_url` | VARCHAR | 500 | YES | NULL | 头像URL |
| `status` | TINYINT | - | NO | 1 | 账号状态（1=启用，0=禁用） |
| `last_login_at` | TIMESTAMP | - | YES | NULL | 最后登录时间 |
| `last_login_ip` | VARCHAR | 45 | YES | NULL | 最后登录IP（支持IPv6） |
| `failed_login_attempts` | INT | - | NO | 0 | 失败登录次数 |
| `locked_until` | TIMESTAMP | - | YES | NULL | 账号锁定截止时间 |
| `created_at` | TIMESTAMP | - | NO | CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | TIMESTAMP | - | NO | CURRENT_TIMESTAMP | 更新时间 |
| `deleted_at` | TIMESTAMP | - | YES | NULL | 软删除时间 |

**约束**:
- PRIMARY KEY: `user_id`
- UNIQUE KEY: `username`, `email`
- INDEX: `idx_username`, `idx_email`, `idx_status`, `idx_deleted_at`

### 3.5 工单操作日志表（ticket_logs）

**用途**: 记录工单所有操作历史

**表名**: `ticket_logs`

| 字段名 | 数据类型 | 长度 | 允许NULL | 默认值 | 说明 |
|--------|----------|------|----------|--------|------|
| `log_id` | BIGINT | - | NO | AUTO_INCREMENT | 日志ID（主键） |
| `ticket_id` | BIGINT | - | NO | - | 工单ID（外键） |
| `user_id` | BIGINT | - | NO | - | 操作人ID（外键） |

## 6. 约束与规则

### 6.1 数据完整性约束

#### 6.1.1 非空约束
- 所有主键、外键、创建时间、更新时间字段均为 NOT NULL
- 工单核心字段（title, description, priority, status, category）为 NOT NULL
- 用户核心字段（username, password, real_name, email）为 NOT NULL

#### 6.1.2 唯一性约束
- 用户名、邮箱全局唯一
- 工单编号全局唯一
- 角色代码全局唯一
- 用户-角色组合唯一

#### 6.1.3 外键约束
- 所有外键均设置参照完整性
- 级联删除：user_roles、ticket_logs、ticket_attachments、notifications
- SET NULL：reviewer_id、approver_id（当用户被删除时）

#### 6.1.4 CHECK约束（PostgreSQL）

```sql
ALTER TABLE tickets ADD CONSTRAINT chk_progress 
  CHECK (progress_percentage >= 0 AND progress_percentage <= 100);

ALTER TABLE tickets ADD CONSTRAINT chk_reject_count 
  CHECK (reject_count >= 0);

ALTER TABLE users ADD CONSTRAINT chk_failed_attempts 
  CHECK (failed_login_attempts >= 0);

ALTER TABLE ticket_attachments ADD CONSTRAINT chk_file_size 
  CHECK (file_size > 0 AND file_size <= 10485760); -- 10MB
```

### 6.2 业务规则约束

#### 6.2.1 工单编号生成规则
- 格式：`TK + YYYYMMDD + 4位序号`
- 示例：`TK202609060001`
- 每日从 0001 开始递增
- 通过触发器或应用层实现

#### 6.2.2 状态流转规则
- 工单创建后状态为 `pending_assign`
- 只有 `processing` 状态可以提交审核（变为 `pending_review`）
- 只有 `pending_review` 状态可以审核（变为 `completed` 或 `rejected`）
- 驳回后状态变为 `rejected`，需要处理人重新处理（变回 `processing`）
- 任何状态均可被管理员强制关闭（变为 `cancelled`）

#### 6.2.3 权限规则
- 创建者只能查看和修改自己创建的工单（草稿状态）
- 处理人只能查看和处理分配给自己的工单
- 审核人可以查看本部门或全部工单
- 管理员可以操作所有工单

#### 6.2.4 附件规则
- 单个文件大小 ≤ 10MB
- 单个工单附件总数 ≤ 20个
- 支持格式：jpg, png, gif, pdf, doc, docx, xls, xlsx, txt, zip, rar

#### 6.2.5 通知规则
- 工单创建：通知管理员
- 工单分配：通知处理人和创建者
- 进度更新：通知创建者
- 提交审核：通知审核人和创建者
- 审核结果：通知处理人和创建者
- 工单关闭：通知创建者和处理人

## 7. 性能优化建议

### 7.1 查询优化

#### 7.1.1 常用查询示例

**查询我的待处理工单**:
```sql
SELECT * FROM tickets 
WHERE assignee_id = ? AND status IN ('processing', 'rejected') 
AND deleted_at IS NULL
ORDER BY priority DESC, created_at ASC;
```
**索引**: `(assignee_id, status)` 复合索引

**查询待分配工单**:
```sql
SELECT * FROM tickets 
WHERE status = 'pending_assign' AND deleted_at IS NULL
ORDER BY priority DESC, created_at ASC;
```
**索引**: `(status, priority, created_at)` 复合索引

**查询超期工单**:
```sql
SELECT * FROM tickets 
WHERE expected_finish_time < NOW() 
AND status NOT IN ('closed', 'cancelled') 
AND deleted_at IS NULL;
```
**索引**: `(expected_finish_time, status)`

#### 7.1.2 分页查询优化

使用游标分页代替 OFFSET：
```sql
-- 第一页
SELECT * FROM tickets WHERE deleted_at IS NULL ORDER BY ticket_id DESC LIMIT 20;

-- 下一页（假设上一页最后一条记录的 ticket_id = 12345）
SELECT * FROM tickets WHERE ticket_id < 12345 AND deleted_at IS NULL ORDER BY ticket_id DESC LIMIT 20;
```

### 7.2 索引优化

#### 7.2.1 索引维护
- 定期分析表统计信息（PostgreSQL: ANALYZE, MySQL: ANALYZE TABLE）
- 定期重建碎片索引（PostgreSQL: REINDEX, MySQL: OPTIMIZE TABLE）

#### 7.2.2 避免索引失效
- WHERE 条件避免对索引列使用函数（如 `DATE(created_at)`）
- 使用 `LIKE 'keyword%'` 而非 `LIKE '%keyword%'`
- 避免隐式类型转换

### 7.3 分区策略（可选）

对于数据量超过百万级的表，考虑分区：

**按时间分区（tickets 表）**:
```sql
-- PostgreSQL 示例
CREATE TABLE tickets (
  ...
) PARTITION BY RANGE (created_at);

CREATE TABLE tickets_2026_q1 PARTITION OF tickets
  FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');

CREATE TABLE tickets_2026_q2 PARTITION OF tickets
  FOR VALUES FROM ('2026-04-01') TO ('2026-07-01');
```

### 7.4 缓存策略

#### 7.4.1 应用层缓存
- 用户角色权限缓存（Redis，TTL = 1小时）
- 系统配置缓存（Redis，TTL = 10分钟）
- 工单统计数据缓存（Redis，TTL = 5分钟）

#### 7.4.2 数据库层缓存
- 查询结果集缓存（MySQL Query Cache / PostgreSQL Shared Buffers）
- 热点数据缓存（高优先级工单）

### 7.5 归档策略

#### 7.5.1 定期归档
- 已关闭超过 1 年的工单归档至历史表
- 操作日志按月归档
- 通知消息保留 3 个月后删除

#### 7.5.2 归档表结构
```sql
CREATE TABLE tickets_archive (LIKE tickets INCLUDING ALL);
CREATE TABLE ticket_logs_archive (LIKE ticket_logs INCLUDING ALL);
```

### 7.6 读写分离

对于高并发场景，建议：
- 主库：处理写操作（INSERT, UPDATE, DELETE）
- 从库：处理读操作（SELECT）
- 使用数据库中间件（如 ProxySQL、PgBouncer）
